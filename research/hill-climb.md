# Research for a cstack hill-climb skill

Reviewed 2026-11-10. This is design research, not a skill implementation or an optimization campaign.

## Intended contract

The proposed skill should improve an explicitly selected prompt, program, agent, or harness against a particular evaluation. It should identify weaknesses from actual executions, propose bounded changes, rerun the changed artifact, and preserve candidates whose measured behavior warrants keeping them. A higher development score is evidence for further evaluation; it does not by itself establish general improvement.

The proposed design is framework neutral: reuse the target project's execution and evaluation machinery, then select an optimizer or an agent-led search process appropriate to the artifact. DSPy, Ax, GEPA, and HALO supply different components of that process. Requiring all four would combine overlapping frameworks with a separate diagnostic engine.

## Evidence and source snapshots

Inspected source revisions were [DSPy `4e9db7a`](https://github.com/stanfordnlp/dspy/commit/4e9db7a83e71e4c36315a2402ae7ffd0c6493404), [Ax `3ad7b69`](https://github.com/ax-llm/ax/commit/3ad7b69947e05f1770b1bd6cb1316a8ec7fcd106), [GEPA `ce5b0d6`](https://github.com/gepa-ai/gepa/commit/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309), and [HALO `b7f8509`](https://github.com/context-labs/HALO/commit/b7f8509745d67b499b4e80efe20ea37c03426a74). Key DSPy, Ax, and GEPA files were fetched again using those immutable revisions and matched their inspected branch contents. These snapshots establish source behavior, not the behavior of every published package version.

No libraries were installed, interfaces executed, provider/model calls made, or benchmark improvements reproduced. API descriptions below are checked against definitions and call paths. Recommendations are explicitly design inferences. The supplied GEPA article and Ax website are live pages; a dated article URL does not establish an immutable historical API.

## What each source contributes

| Source | Actual role | Useful adoption point | Material limitation |
|---|---|---|---|
| DSPy | Python LM-program framework with optimizer integrations | Existing DSPy modules, metrics, traces, and examples | Native optimization targets must be represented within its program model |
| Ax | Separate DSPy-style framework; inspected TypeScript implementation includes GEPA and bootstrapping | Existing Ax programs and TypeScript evaluation infrastructure | Similar algorithm names do not imply Python-package interoperability or identical defaults |
| GEPA | Reflective evolutionary search algorithm and Python package; `optimize_anything` is a broader API | Text artifacts evaluated through an existing project runner | Needs a credible evaluator; budgets and data exposure require explicit accounting |
| HALO | Trace analysis engine and external improvement methodology | Diagnose recurring failures before proposing code changes | Diagnosis does not implement candidate execution, acceptance, or promotion |

These distinctions follow the implementations discussed below. The table's adoption guidance is inference, not a measured comparison.

## DSPy: optimize a represented program

DSPy's GEPA integration explicitly imports its optimization engine from the separate `gepa` package. Its public shape is `dspy.GEPA(metric=..., reflection_lm=..., max_metric_calls=...).compile(student, trainset=..., valset=...)`. Exactly one of `auto`, `max_full_evals`, and `max_metric_calls` must be supplied. The metric must accept five arguments: gold example, prediction, trace, predictor name, and predictor trace. It may return numeric scores or scored textual feedback. Predictor-specific feedback lets proposals address the responsible module rather than only the final answer. ([DSPy GEPA implementation](https://github.com/stanfordnlp/dspy/blob/4e9db7a83e71e4c36315a2402ae7ffd0c6493404/dspy/teleprompt/gepa/gepa.py))

The integration captures execution traces, creates a candidate mapping from predictor instructions, and also recognizes current `dspy.Flex` code components. It passes that representation through `DspyAdapter` to `gepa.optimize`. Therefore “GEPA in DSPy only rewrites prompt strings” is now too narrow; “DSPy automatically optimizes arbitrary repository files” is too broad. Train examples drive reflection; validation examples track candidate quality. Omitting validation uses the training examples for both. `track_stats=True` exposes detailed results; these integration conveniences do not create an independent final test. ([Same implementation and seed construction](https://github.com/stanfordnlp/dspy/blob/4e9db7a83e71e4c36315a2402ae7ffd0c6493404/dspy/teleprompt/gepa/gepa.py#L542))

MIPROv2 is a different search strategy, not another name for GEPA. Its implementation bootstraps demonstration candidates, proposes instructions using program/data context, then searches combinations with Optuna's multivariate TPE sampler. It evaluates minibatches and periodically performs fuller evaluations. Its interface is `MIPROv2(metric=..., auto=...).compile(student, trainset=..., valset=...)`; current source treats Optuna as an optional dependency. Defaults also construct a validation split when one is absent. A generic skill should define its own dataset contract rather than silently inherit those split choices. ([MIPROv2 source](https://github.com/stanfordnlp/dspy/blob/4e9db7a83e71e4c36315a2402ae7ffd0c6493404/dspy/teleprompt/mipro_optimizer_v2.py))

Design inference: adopt these optimizers where the project already exposes DSPy modules. Translating an unrelated agent into DSPy merely to start hill climbing adds a migration and may change the evaluated system. Also avoid treating metric-call budgets as total request or dollar budgets: a program execution can invoke many models/tools, and this DSPy GEPA integration explicitly rejects `max_reflection_cost` because its LM interface does not expose the required cumulative cost accounting. ([GEPA budget checks](https://github.com/stanfordnlp/dspy/blob/4e9db7a83e71e4c36315a2402ae7ffd0c6493404/dspy/teleprompt/gepa/gepa.py#L492))

## Ax: related ideas, a separate implementation

[Ax's website](https://axllm.dev/) describes DSPy-style programming and native libraries in several languages. The implementation inspected here is TypeScript in `ax-llm/ax`, rather than a claim of optimizer parity across all those libraries. Its `optimize(program, examples, metricFn, options)` helper instantiates `AxGEPA`; depending on configuration and example count, it composes `AxBootstrapFewShot` before GEPA. It measures the unmodified baseline first and supports explicit `maxMetricCalls`. Installing Python DSPy or GEPA is not what implements this helper. ([Ax optimize source](https://github.com/ax-llm/ax/blob/3ad7b69947e05f1770b1bd6cb1316a8ec7fcd106/src/ax/dsp/optimize.ts))

`AxGEPA.compile(program, examples, metricFn, options)` requires a positive metric-call budget and optimizable program components. Scalar metrics receive `{prediction, example}`; multi-metrics return named numeric scores. Options include `validationExamples`, `feedbackExamples`, textual `feedbackFn`, and a custom `gepaAdapter` with evaluation, reflective-dataset, and optional proposal hooks. Thus an Ax project can adapt an existing evaluator rather than replace its grader. ([GEPA compile](https://github.com/ax-llm/ax/blob/3ad7b69947e05f1770b1bd6cb1316a8ec7fcd106/src/ax/dsp/optimizers/gepa.ts#L266), [shared types](https://github.com/ax-llm/ax/blob/3ad7b69947e05f1770b1bd6cb1316a8ec7fcd106/src/ax/dsp/common_types.ts), [adapter contract](https://github.com/ax-llm/ax/blob/3ad7b69947e05f1770b1bd6cb1316a8ec7fcd106/src/ax/dsp/optimizers/gepaAdapter.ts))

Ax implements its own per-instance parent sampling, reflective mutations, multi-objective archive, and scheduled component merging. It also caps the selection set using `paretoSetSize`: supplied validation examples are sliced, so “passed the validation set” need not mean every supplied example was evaluated. This is a design-changing integration detail, not an effectiveness verdict. A cstack adapter must record the actual evaluated membership and verify shortlisted candidates through the project's full required checks. Do not assume a familiar algorithm name gives identical selection, accounting, resume, or validation behavior across implementations. ([Ax GEPA source](https://github.com/ax-llm/ax/blob/3ad7b69947e05f1770b1bd6cb1316a8ec7fcd106/src/ax/dsp/optimizers/gepa.ts))

## GEPA: feedback-driven search beyond prompts

The supplied [optimize_anything article](https://gepa-ai.github.io/gepa/blog/2026/02/18/introducing-optimize-anything/) presents three modes: search for one solution without a dataset; cross-transfer among dataset tasks; and learning a reusable artifact with dataset plus validation examples. Its central transferable idea is evaluator feedback richer than one score, coupled with retaining complementary candidates. Its performance examples are author-reported demonstrations, not evidence that a cstack campaign will obtain similar gains.

Current pinned source exposes `optimize_anything(seed_candidate=..., evaluator=..., dataset=..., valset=..., test_set=..., config=OptimizeAnythingConfig(...))`. The evaluator receives candidate text, plus an example when applicable, and returns a higher-is-better score with optional diagnostic information. Seeds can be strings or named text-component dictionaries; dictionary support is specific to the GEPA engine. This is a practical seam for invoking the target project's CLI, test suite, or agent runner. It does not require rewriting that product as a DSPy or Ax program. ([Current public API](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/optimize_anything.py))

The live article examples use `GEPAConfig` with `EngineConfig(max_metric_calls=...)`. Current source retains that surface through a legacy launcher, while the newer `OptimizeAnythingConfig` selects an engine and exposes `max_evals` and `max_token_cost`. The latter API includes other engines, such as `best_of_n`, `autoresearch`, and `meta_harness`. “Use optimize_anything” therefore does not fully specify the search algorithm or operational requirements. Pin an implementation and configuration before writing runnable integration instructions. ([API dispatch](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/optimize_anything.py), [configuration](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/oa/config.py))

Actionable Side Information is a dictionary containing evidence useful for diagnosis: actual versus expected outputs, failed assertions, tracebacks, tool results, profiler data, or rendered images for a vision-capable proposer. Named `scores` can carry additional higher-is-better objectives. This information guides proposals; it is not itself an acceptance test. Design inference: preserve exact case IDs and evidence references, and distinguish verifier facts from a model's hypotheses. Do not give the proposer only an average score, or flood its context with every trace. ([SideInfo definition and handling](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/gepa_launcher.py#L183))

GEPA's candidate selection is materially broader than greedy hill climbing. Per-example front membership preserves specialists; parent sampling favors candidates covering those fronts, after removing redundant coverage. Optional merging combines component choices from compatible descendants of a common ancestor and evaluates the result. This is not an unrestricted semantic merge of arbitrary repository patches, nor a guarantee that every nondominated candidate survives. Design inference: keep search retention separate from final promotion, and permit a small complementary archive where useful rather than requiring every proposal to beat one incumbent's average. ([Candidate-selection utility](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/gepa_utils.py), [merge implementation](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/proposer/merge.py))

Operational boundaries matter. New-API `max_evals` caps evaluation-server calls, while `max_token_cost` caps optimizer/proposer token spend, not the whole application's execution cost. Custom callables without meaningful cost reporting cannot provide reliable dollar accounting. The legacy path checks its metric-call bound between iterations. GEPA state supports resume from `run_dir`; that does not justify reusing a checkpoint after changing examples, grader semantics, environment, or stochastic policy. ([Engine integration](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/oa/engines/gepa.py), [legacy dispatch](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/optimize_anything.py), [resume contract](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/api.py))

Validation participates in adaptive candidate selection, so it is development evidence even when called held out. Current `test_set` avoids the optimization server and scores the seed and selected candidate separately, outside the eval budget; final-test exceptions become zero scores. Reserve final-check budget independently and preserve infrastructure errors distinctly in the campaign record. Keeping tests out of this server is not an access-control guarantee against a proposer with broader filesystem access. Repeatedly using final-test results to guide changes also exposes that set. ([Test execution source](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/optimize_anything.py#L428))

## HALO: improve diagnosis before changing code

HALO's concrete contribution is trace investigation. Its [AppWorld walkthrough](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/demo/appworld/README.md) runs tasks, obtains traces and eval reports, analyzes failures, edits the harness, and reruns the same split. The diagnostic engine produces evidence and proposed fixes; code changes and evaluation happen externally.

Current engine APIs accept messages, configuration, and one or multiple trace paths. Optional repository access is read only. Prompts direct analysis from dataset discovery to indexed filtering to selected trace evidence, and warn that an absence of error-status spans does not prove task success. This discipline is useful with any project's logs. Parts of the bundled workflow skill describe older restrictions, including traces-only access; current code is the stronger interface authority. ([Engine](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/engine/main.py), [configuration](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/engine/engine_config.py), [prompts](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/engine/agents/prompt_templates.py))

Running HALO adds Python/Agents SDK dependencies, provider configuration, trace ingestion, and Deno/Pyodide analysis tooling. Hosted inference.net service is optional. These are requirements of that implementation, not prerequisites for trace-informed hill climbing. Its optional root-conversation checkpoints are not a campaign's candidate/score/spend ledger. Design inference: borrow its evidence discipline by default; adopt the engine only when trace scale and existing infrastructure justify it. ([Dependencies](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/pyproject.toml), [sandbox](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/engine/sandbox/README.md), [checkpoint events](https://github.com/context-labs/HALO/blob/b7f8509745d67b499b4e80efe20ea37c03426a74/engine/models/engine_output.py))

## Recommended framework-neutral campaign

The following is a design synthesis, not an interface promised by any source:

1. **Freeze the contract.** Identify editable files/components, initial revision, actual runner command, case contents and schemas, graders/rubrics, environment, model settings, and source authority. Hash inputs and configuration. Matching IDs and expected labels alone does not establish faithful evaluation semantics.
2. **Run the baseline.** Execute the product or agent to obtain fresh outputs, traces, scores, and costs. A stored-output grading package can establish grader behavior; regrading unchanged outputs cannot measure a changed prompt or harness.
3. **Diagnose and propose.** Cluster observed failures, inspect representative evidence, state a falsifiable hypothesis, and make an attributable change within scope. A framework optimizer may manage proposals; an agent may do the same through existing tools.
4. **Evaluate and retain.** Run the changed artifact under the frozen contract. Record per-case outcomes, resource usage, failures, parentage, and evidence. Use cheaper screening only as screening. Keep the best feasible incumbent and any deliberately retained complementary candidates; reject invalid or constraint-breaking candidates.
5. **Validate and promote.** Compare shortlisted candidates on the agreed confirmation protocol and regressions. Make the final promotion decision with independently reserved checks where available. Report uncertainty and remaining limits; deliver the winning diff plus baseline comparison, rather than only a score.
6. **Stop and preserve.** Enforce the agreed budget and stopping policy, retain the best measured artifact even if the last proposal fails, and persist enough provenance to resume only the same campaign contract. If the evaluator is defective, repair it as separate work and establish a new comparable baseline.

## Decisions the skill must obtain or make explicit

Recover existing choices from the project and conversation first. Ask only for missing owner judgments that materially change the campaign; technical facts already present in the project do not need another interview.

- **Editable artifact:** prompt text, demonstrations, tool descriptions, model configuration, program code, agent control flow, or broader harness. Evaluation inputs, grader, and hidden answers are outside that scope unless a separately authorized task changes them.
- **Frozen evaluation:** exact cases, schemas, provenance, grader versions, runner, environment, and allowed feedback. Decide whether success means these tasks or generalization to future tasks.
- **Objective and constraints:** primary score, direction, aggregation, important slices, regressions, latency/cost limits, and failure treatment. Do not invent universal score gains or regression allowances.
- **Exposure:** search examples, adaptive selection examples, confirmation cases, and final tests; which labels, traces, and scores the proposer can inspect. A single-set campaign can be useful but supports narrower claims.
- **Stochastic protocol:** baseline/candidate repeats, seeds, temperatures, judge settings, cache behavior, and paired comparisons where meaningful. Repeats are experimental trials, not automatically interchangeable with product majority voting.
- **Budget:** model roles, evaluation calls, optimizer calls, actual tokens/dollars, compute, elapsed time, concurrency, and reserved final checks. No framework's single counter reliably substitutes for all of these.
- **Retention, stopping, promotion:** greedy or archive search, admissibility gates, what improvement merits confirmation, plateau handling, budget exhaustion, and the evidence needed to promote. Keep decisions project-specific and distinguish a promising development result from verified generalization.

The research supports a reusable experimental workflow with optional adapters. It does not establish a universal best optimizer, justify installing a framework automatically, or demonstrate that any particular campaign will improve its target.
