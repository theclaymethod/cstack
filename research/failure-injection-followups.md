# Failure injection follow-ups for C Stack

Research date: 2026-11-10. These are proposals for later implementation, separate from the adversarial-cases sub-skill being built now. This investigation read local source and primary external material; it installed no framework, ran no new fault experiment, and used no paid provider or cloud mutation. Suggested budgets below are proposed ceilings, not measured runtime or efficacy.

## What the existing audit establishes

The useful starting point is the real lifecycle gap in the [Hill Climb ledger](../evals/hill-climb/CROSS_EXAMINE_LEDGER.md): a proposal or confirmation had completed native execution, but interruption before the campaign completion commit stranded its evidence. The repaired evaluator reconciles complete identity-matching receipts without rerunning the candidate or changing charged spend. Partial or incompatible evidence remains pending and charged. The original/repaired replay and already-correct committed-receipt control are valuable regression seeds; a new injector should preserve them rather than replace them with synthetic receipts.

Local source was inspected at checkout HEAD `227c7746ded27a9fb3b4167d1927c78982ac5c9b`, with the working-tree files as observed. In [evaluate.py](../fixtures/playground/evaluate.py), `run_suite` executes actual candidates, flushes and fsyncs trace rows, writes its summary, then returns to `execute_attempt`; completion and campaign publication follow. `write_json` flushes/fsyncs a temporary file and uses `os.replace`. These are concrete boundaries to probe, not a complete power-loss model.

Observed SHA-256 identities: evaluator `c0af96b600a53ae0089f8b9f7c8ddfd20cbc6588dfe1aca625361fe532c85ee9`; interruption hook `0983cbe7a300f17014f8e1cbdaed8d71ef6a12e03e743696ec7d01c8c5c079fc`; ledger `45962011dc3abb1fffe807668a7910ce44aa248d9dd8f8b1e71a9942c4a4ba8d`. These identify the read artifacts even if HEAD does not describe subsequent working-tree changes.

The historical [interrupt_cli.py](../evals/hill-climb/evidence/cross-examine/interrupt_cli.py) stops at a Python line event when the function name, runner path, role, and presence of the local `summary` match. It calls `os._exit(99)`. Python documents that `_exit` skips cleanup handlers and stdio flushing; that differs from raising an ordinary exception and running `finally` blocks. It also differs from losing host power or corrupting storage. [Python `os._exit`](https://docs.python.org/3.14/library/os.html#os._exit).

Line/function hooks are useful for frozen historical versions, but fragile as future APIs: a `line` event occurs before a line executes, `return` events can also arise during exception handling, tracing is thread-specific, and a hook error unsets tracing. A matching function name or configured line does not prove the intended operation completed. Python also identifies `settrace` as an implementation detail rather than a language guarantee. It does not itself control native I/O completion, subprocesses, or scheduling. [Python tracing contract](https://docs.python.org/3.14/library/sys.html#sys.settrace).

## Common experiment contract

Every pilot should freeze a falsifiable user-visible hypothesis before injecting: for example, “after interruption, complete matching evidence is recovered once, partial evidence cannot promote, and charged spend never decreases.” The chaos-engineering principles explicitly pair measurable steady state, a hypothesis, an experimental variable, and a control comparison. Applying that experimental structure locally is useful; it creates no claim about production resilience. [Principles of Chaos Engineering](https://principlesofchaos.org/).

Record fault **requested**, boundary **reached**, action **performed**, and downstream **effect observed** separately. A configured proxy or an armed hook is not an activation witness. Have the operator own the receipt: boundary identifier, occurrence, command, PID, source hashes, action, timestamps, exit status, relevant before/after hashes, and independent state inspection. A supervisor can receive a boundary notification over a pipe, acknowledge it, and kill the blocked child; record the supervisor's action and inspect the surviving files. Failure to reach or acknowledge the boundary is an infrastructure result, not a clean pass.

For each treatment, run the same healthy workflow and an armed-but-no-op control from separate clean copies. Keep operator fault configuration and receipts out of candidate inputs. Label operator-injected environment failures separately from candidate-authored exploits; host permissions and instructions do not enforce isolation. The [playground AGENTS.md](../fixtures/playground/AGENTS.md) and [Cross-Examine ledger guidance](../skills/cross-examine/references/ledger.md) already require these access/claim distinctions.

Reset means a fresh workspace/campaign, restored source and input hashes, cleared injector counters, fresh owned processes, and a checked initial-state manifest. Recovery deliberately restarts against retained treatment state; it must not secretly reset the evidence being tested. Archive each failed state before reduction. A minimal reproducer must still activate the fault, preserve access limits, and fail the same observable invariant in the original version while passing the repaired version and legitimate controls.

## Five bounded pilots

### 1. Named lifecycle failpoints and a crash matrix

**First choice.** Add a small test-only boundary interface in a disposable experimental evaluator, later considered for canonical adoption. Suggested names: `reservation.published`, `trace.row.synced`, `suite.summary.published`, `attempt.completion.published`, and `selection.published`. Specify whether each means before or after the underlying operation; version changes in that meaning. Count occurrences and select exactly one role/attempt/occurrence. Do not let a marker manufacture completion evidence.

Named, selectively enabled failpoints have a concrete precedent in PingCAP's Go implementation: named injection sites, count/probability terms, and actions including pause or panic. That is design inspiration, not a Python dependency or API recommendation. [PingCAP failpoint source and examples](https://github.com/pingcap/failpoint#how-to-inject-a-failpoint-to-your-program).

Run the existing frozen replay first. Then exercise five boundaries for baseline, proposal, and confirmation with one abrupt stop and one no-op treatment each: at most 30 scenario runs, plus healthy controls. Use only disposable materialized workspaces and the native evaluator. Charge actual case executions within each campaign; separately count all campaign starts, controls, and replay work in the experiment budget. Cap the experiment at ten minutes and preserve unfinished work as incomplete.

**Acceptance:** witness each reached boundary; after restart, reconcile complete evidence exactly once, retain pending charges for incomplete execution, preserve the best verified artifact, and recover repeated `verify`/`finish` without new candidate execution. Check actual trace/summary bytes and reservation identity. This establishes process-crash recovery at named boundaries, not disk durability under power failure.

### 2. Generate and minimize stateful command sequences

Use Hypothesis to compose native operations such as start, propose, interrupt, verify, finish, and verify again, plus valid/invalid evidence conditions. Maintain a deliberately smaller reference model of reserved spend, completed identity-matching evidence, incumbent eligibility, and terminal delivery. Assert these observable invariants after every operation. Hypothesis's `RuleBasedStateMachine`, rules, bundles, and preconditions generate action sequences; the library does not supply the correct campaign model. [Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html).

Start with 20 generated sequences of at most eight operations, one active campaign per sequence, and an external 200-command/ten-minute ceiling covering shrinking and retries. `settings(max_examples=20, stateful_step_count=8, deadline=None)` describes exploration, not a strict total execution budget: rejected cases and shrinking require additional work. Use a supervisor limit independent of Hypothesis. `derandomize=True` stabilizes generated choices only while the test, Python, and Hypothesis versions remain compatible; it does not make OS behavior deterministic. [Hypothesis settings API](https://hypothesis.readthedocs.io/en/latest/reference/api.html#hypothesis.settings).

The inspected docs identify version 6.170.15; pin the eventual installed package and record its artifact hash before a pilot, rather than assuming a floating `latest` URL is a reproducibility pin. Preserve the minimized explicit command sequence, fixtures, boundary schedule, and source versions alongside any seed/database entry. Hypothesis supports replay from its example database and explicit failures, but a readable native replay remains the durable audit artifact. Shrink only when the same fault activates and the same invariant fails; otherwise minimization has changed the mechanism. [Hypothesis replay documentation](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html).

### 3. Fail selected storage operations once and persistently

Wrap only the experimental runner's relevant storage boundary: writing trace/summary/state data, fsync, and rename. Inject a real `OSError` at a selected operation, recording its name and occurrence. First test one failure followed by healthy I/O; then keep failing that operation class after the trigger. SQLite's primary testing account uses this exact distinction and advances the failure point through I/O operations, then checks integrity after disabling injection. Its crash simulation separately models unsynchronized writes, demonstrating why process exit and storage-fault simulation answer different questions. [SQLite anomaly testing, sections 3.2–3.3](https://www.sqlite.org/testing.html).

Start with four selected operations × two persistence modes × three controls/treatments, capped at 24 scenarios and ten minutes. Limit patching to the runner process; do not globally replace host filesystem functions, fill a real disk, chmod user directories, or alter canonical receipts. Check that previously published JSON remains readable, failed writes do not become accepted completion, old evidence stays intact, and temporary/lock handling permits a clean retry when appropriate. A wrapper-raised `ENOSPC` is a simulated API failure, not measured real disk exhaustion. Partial writes need their own explicit write-prefix model; merely raising before a write does not test them.

### 4. Subprocess deadlines and partial output

Use dedicated synthetic candidates in disposable workspaces: wait indefinitely, emit a JSON prefix then wait, emit valid output then exit nonzero, and exit successfully with malformed output. Pair each with a healthy candidate and instrumented no-op run. Prefer an explicit readiness handshake over timing a sleep to target the prefix-written state. The native grader, not the candidate, decides whether a case is complete.

Python's `subprocess.run(timeout=...)` kills and waits for its child on expiration, but process creation itself may delay the timeout; `Popen.communicate(timeout=...)` has a different cleanup contract. Therefore record observed termination and captured bytes rather than equating timeout configuration with successful cancellation. Descendants need separate process-group ownership if a later fixture creates them. [Python subprocess contracts](https://docs.python.org/3.14/library/subprocess.html#subprocess.run).

Use four treatments plus controls, a 35-second supervisor ceiling per native development-suite invocation, and a two-minute total ceiling. This accommodates eight cases at the fixture's existing three-second case timeout without changing its frozen configuration; a supervisor cutoff still leaves incomplete evidence. Verify ERROR classification, reservation accounting, no promotion from partial output, and cleanup of owned child processes. Test a transient first-attempt failure separately from persistent failure; the current evaluator's ordinary timeout must not silently become a free retry. AWS's guidance explains the deeper requirement: a timeout does not establish that side effects did not occur, and retrying can duplicate effects or amplify overload. [AWS timeouts and retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).

### 5. Optional loopback dependency faults

The current support-agent fixture has no real network dependency, so a proxy adds little today. Later, build a separately scoped local HTTP dependency adapter and route it through Toxiproxy. Use a native local binary, loopback-only control/data listeners, no external upstream, and no Docker requirement. Pin the evaluated API to [Toxiproxy v2.12.0](https://github.com/Shopify/toxiproxy/releases/tag/v2.12.0), commit [`3ccd6a79cbc6c6a72b884d295ad314b75cdf3962`](https://github.com/Shopify/toxiproxy/commit/3ccd6a79cbc6c6a72b884d295ad314b75cdf3962); confirm architecture and binary checksum during setup. This is a reviewed pin, not a claim that it is newest.

The pinned API supports proxy creation, toxic creation/removal, version inspection, and reset. Useful treatments are downstream `timeout`, `reset_peer`, and `limit_data`; zero-timeout stalls until removal, while `limit_data` closes after a byte threshold. Set `toxicity=1` and zero jitter for the first deterministic treatments. Use Python's standard HTTP client for the control API rather than introducing an unverified Python wrapper. [Pinned Toxiproxy README/API](https://github.com/Shopify/toxiproxy/blob/v2.12.0/README.md#http-api).

Run three treatments plus direct and proxy no-op controls, at most 20 requests/two minutes. Capture the proxy configuration, server request/commit log, client error, and surviving task state. Include “server committed, reply lost” with an idempotency key; request counts and unique committed operations distinguish harmless retry from duplication. Remove only this experiment's toxics/proxy in cleanup; global `/reset` would affect other tests sharing a daemon. Restricting the pilot to its own daemon avoids shared state entirely. A successful toxic API response alone does not prove traffic traversed the proxy.

## Defer heavier systems

FoundationDB's deterministic simulator runs its database with workloads and injected faults in a controlled simulation; this requires ownership of nondeterminism rather than adding a seed to arbitrary host execution. Borrow explicit schedule records now; defer a simulator until concurrency and nondeterministic dependencies justify the architecture. [FoundationDB SIGMOD 2021 paper](https://www.foundationdb.org/files/fdb-paper.pdf).

Jepsen separates a nemesis from clients and checks operation histories, including uncertainty about whether failed calls took effect. That is an excellent evidence model for a future multi-node service, but cluster provisioning, Clojure tooling, and network-control scope add little to this local Python runner. [Jepsen's fault tutorial](https://github.com/jepsen-io/jepsen/blob/main/doc/tutorial/05-nemesis.md). CrashMonkey/ACE test bounded filesystem workloads and persisted-state consistency using Linux filesystem machinery; reserve them for a dedicated Linux VM/storage investigation, not the current macOS playground. [CrashMonkey project source](https://github.com/utsaslab/crashmonkey).

Implement pilots 1 and 4 first, then 2 and 3; revisit 5 only with a real dependency contract. None has measured efficacy in C Stack yet. Keep clean observations, failures to activate, infrastructure errors, and confirmed invariant violations distinct, and report only the versions, boundaries, schedules, and access conditions actually replayed.
