# Calibration contract and evidence

Use the project's existing data, runner and case representation. A judge calibration over stored labeled outcomes need not acquire a new environment format. Harbor remains preferred for new executable agent tasks; see [format selection](../../create-eval/references/formats.md).

## Audit gold before fitting

Recover the original evaluated artifact and precise label scope, authority and criterion revision. An approved reference answer is potentially permitted task evidence; a human verdict on this output is supervision. Keep the distinction explicit. Preserve individual annotations and later adjudication separately. When independent human labels exist, report their reliability as context; do not invent it or treat it as a mathematical performance ceiling.

Flag contradictory, unsupported and incomplete labels for owner review. Do not relabel them to improve a fitting score. A synthetic rule can support fixture-derived expected outcomes without becoming human approval. Keep uncertainty and any exclusions visible by class and source.

Group dependent records before assigning partitions: source tasks/documents, duplicates, transformations, shared templates and connected ancestry. Use grouped development folds when needed, and reserve independent final evidence when sufficient data exists. A split name does not enforce blindness. Small or fully exposed data can establish development results while leaving final calibration unsupported.

## Freeze the measurement

Record original criterion meaning, input projection/allowed references, label and family identities, partition/exposure history, backend/model version, prompt/questions/examples, parser, thresholds/calibrator, repeats/cache/retry policy and budget. Keep unknown version facts explicit.

The fitting/selection process may access authorized development labels. The judge receives only declared runtime evidence. Protect comparator assets with actual access controls when the claim depends on enforced separation. An allowlist and an ordinary host process establish an inspected input boundary, not containment against a malicious process.

Preserve predictions and raw responses before comparison reads gold. Require exact case/check membership, unchanged source/configuration and consistent raw-to-parsed decisions. A candidate manifest or matched empty inventory is not proof that required judging occurred. Keep errors and partial reservations visible on interruption; use fresh identities for new work and preserve previous attempts.

Anchor completed response/content digests in the operator-owned run record, then verify both content and adjacent manifests against that record. Rewriting output and its neighboring hash must not create a new accepted result. Hashes provide consistency checks; protection against a hostile writer still depends on actual access controls.

Freeze the exact final candidates and confirmation policy before prediction. Complete and freeze the planned baseline/candidate outputs before exposing final labels. Block further fitting against consumed final evidence through the project's exposure record. Read-only reporting of the same frozen results is different from another selection attempt. A new context or renamed split does not erase prior exposure.

## Handoff and readiness

Deliver the selected judge artifact/configuration and invocation, dataset/split/source identities, raw baseline/candidate outputs, before/after reports, acceptance policy, budget use, rejected candidates and remaining uncertainty. State whether observed support is schema-only, mocked, SDK-tested, provider-executed or calibrated against human labels. Declare actual provenance rather than deriving authority from a file called gold.

If setup, gold, policy or evidence is insufficient, return a concrete draft plus blockers and retain a recoverable baseline. Offline validation can check arithmetic, leakage guards, state transitions and response normalization. It does not certify a live judge. Keep release readiness separate from “the mechanics passed.”

Use [Run Eval](../../run-eval/SKILL.md) for faithful execution/reporting, [Hill Climb](../../hill-climb/SKILL.md) for optional search and [Cross-Examine](../../cross-examine/SKILL.md) for independent review of suspected shortcuts. Changing the evaluator during product optimization starts a new evaluation boundary and comparable baseline.

Source: [grouped validation guidance](https://scikit-learn.org/stable/modules/cross_validation.html). The repository's `research/judge-calibration.md` records the primary-source investigation; these instructions work without that development note or the playground being installed.
