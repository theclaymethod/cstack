# Adversarial Cases: construct a controlled challenge

Use a disposable workspace. This shared builder is normally reached through Bootstrap or Cross-Examine; you can invoke `$adversarial-cases` directly to practice construction. The parent keeps expectation approval and finding/repair adjudication.

Handoff:

> Use Adversarial Cases to construct a small challenge set from this fixture's original synthetic spec and observable execution boundaries. Include one lifecycle fault, one scoring-boundary case, clean and legitimate-alternative controls, and an armed-but-unreached/no-op control. Use the existing runner and permitted copies of supplied exercise artifacts. Write drivers, candidate variants, receipts, and proposed review cards under eval-runs/case-build. Keep the canonical runner/spec/cases/rubric unchanged. Trace or interrupt only your own local test processes; record that operator access separately from candidate access. Bound this exercise to 120 actual case executions and four process interruptions, with no provider/network calls. Preserve activation witnesses and independently observed outcomes. Reduce each case while keeping its mechanism and controls; report non-activation or no demonstrated defect honestly.

Completion requires actual evidence rather than a configured fault label:

- Original requirement, source/version, feasible setup, and explicit candidate/operator permissions.
- A real boundary reached and perturbation observed, or an explicit not-activated result.
- Actual output/state, native score, independent outcome witness, clean/alternative controls, and rejected/retained reductions.
- Bootstrap-ready guessed expectations left pending review, and a Cross-Examine handoff left unadjudicated.

The current native campaign is intended to recover complete identity-matching measurements. An injected interruption may demonstrate correct recovery. The separately supplied `exercises/fixtures/verify_claim.py` is deliberately defective; name its version and distinguish its behavior from the native grader. A case builder should not invent a new current-system flaw to make the exercise look successful.

Future stateful generators, named failpoints, solver/proxy tooling, and broader fault schedules are research proposals in C Stack's `research/` notes. This exercise does not install or require them.
